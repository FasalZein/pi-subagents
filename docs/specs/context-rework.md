## Problem Statement

I run long Pi sessions that delegate work to children. Two things go wrong.

The parent's context fills up. Each agent definition I add makes the parent prompt longer, because the roster lists every agent with every model it accepts. Each child that finishes puts its whole final message into the parent, with no limit. One report in my sessions was 29,993 characters. When I launch a batch, every result costs a parent turn and stays in context for the rest of the session.

The orchestration is not reliable enough to lean on. A parent cannot ask for the results of children it launched earlier, so it either blocks at launch or waits for messages one by one. Scratch tests against v2.9.2 reproduced a result that arrived twice, a result that nobody delivered, and a result that waited until I typed. A failed launch can leave an empty pane open. A background child that I stop is reported as completed or failed. A pane that I took over can close by itself. One malformed agent file stops every agent.

Measurements on 8 of my parent sessions (705 requests) corrected one belief. The extension's own text is about 4.4% of parent input. The parent's own tool calls and their results (reading, commands, and the code of those calls) are about 57%. So the larger saving is a parent that hands a batch to children and never sees the intermediate results.

I also move from the old herdr TUI to the Herdr app on herdr-core, and I use Rex. Neither has a backend. Each existing backend is a set of branches spread over at least seven files.

## Solution

A parent's context cost for delegation becomes flat and bounded, and delegation becomes dependable.

- I can add any number of agent definitions. The parent prompt holds a short index with a fixed maximum size. Full detail about one agent loads when the parent asks for it or when a launch needs it.
- Every run that ends while its parent watches it ends in one result with a typed outcome. The parent gets a summary of at most 1,500 characters and the path of a report file. The full report never enters the parent by itself.
- A parent can wait for runs it launched earlier. A workflow script can launch a batch, wait, branch on typed data, and return one digest, so the reports of the batch stay out of the parent.
- Each result reaches the parent by itself, in a wait reply or as a message; results ready at one turn boundary arrive as one message. A result never waits for me to type, unless I pressed Esc as it arrived. The extension does not check whether the model read a result. A result the parent did not see is fetched again by run id or found in a list of recent runs, and every copy has the same size limit.
- Launch, stop, resume and takeover behave as their names say, and one bad agent file affects only that agent.
- deny-env holds on herdr-core, Rex and old herdr. On tmux, cmux, WezTerm and Zellij a denied name with the backend's prefix can still reach a child, a known limit (D34). Pane children work in the Herdr app through herdr-core and in Rex, behind one backend interface that the five existing backends also use.

There is one mode. It has no setting of its own; the spawn width of v2.9.2 limits concurrent runs (D9, amended 2026-11-20).

## Implementation Decisions

### Foundations

**D1. Fork and branch.** All work stays in the fork on branch feat/context-rework. Nothing is pushed and nothing is merged to main. No GitHub issue, comment or pull request is published. The owner uses the branch locally until upstream v3 arrives.

**D2. Pi version.** The extension requires Pi 1.5.2 or later. Compatibility with 0.85 ends. The peer and development dependencies move to 1.5.x, the pi-server pin is removed, and the one test fixture that fails to typecheck on 1.5.2 is fixed.

**D3. One mode.** Orchestrator mode is removed with its controller, configuration, policy, prompt, overlay view, environment switch and tests. No handler in a parent session returns a whole system prompt; prompt additions use named sections or the append collection that Pi provides. A child keeps its whole-prompt returns (the time-limit text, and the composition of skills and appended system text) until D33 moves them (owner, 2026-11-18). The switch that turns off the coordinator-only turn (PI_SUBAGENT_DISABLE_COORDINATOR_ONLY_TURN) stays. The README gets a short migration note for the removed delegation-only restriction; there is no second mode.

**D4. Compatibility surface.** These stay as they are in v2.9.2: every agent frontmatter key and its meaning; the tool names subagent, subagent_resume, subagent_kill, subagent_done, caller_ping and set_tab_title; the environment variables; the launch metadata entry in child sessions; the message type subagent_result. Additions are new and optional: the frontmatter key pinned, the tools subagent_wait and subagent_agents, new optional tool parameters, no environment variable for launch admission (D9, amended 2026-11-20: PI_SUBAGENT_LAUNCH_CAP is removed). Removed on purpose: the roster message (D19), the subagent_ping message type for new deliveries (D12), and orchestrator mode (D3). Old sessions with roster or ping messages still load and render. The unused fork session manager module stays until the rebase (owner accepted the cut, 2026-11-18).

### Runs

**D5. Run record.** One run has one record with one phase field and, at the end, one outcome. Phases: starting, running, soft limit reached, wrapping up, stopping, ended. The flags that today express the same facts (the dead execution-state field, the three delivery flags, the separate timeout markers) are derived from the phase or removed. The old delivery flags are deleted only after every consumer reads the phase.

**D6. Launch undoes what it made.** A launch registers each thing it creates as it creates it: the seeded child session file, the surface, the environment capsule, the spawn slot. When a later step fails, the launch removes them in reverse order and then reports the error. A spawn slot is released only by the run that holds it. This fixes the open pane after a failed launch and the double slot release after a failed verified fan-out. A resume never deletes or changes the session it resumes.

**D7. Stop and abort.** A stop request decides the outcome. A run that was asked to stop ends as cancelled on every backend and for headless children, whatever the dying child wrote. The abort signal of a tool call reaches every wait except the wait of an explicitly synchronous launch (async: false, also when the parent has no durable turn), which ignores it as in v2.9.2 (amended 2026-11-20, parity D04a; owner 2026-11-20T12:00Z). A time limit that expires gives timed out, never cancelled. Without a stop, the first outcome that reaches the exit record wins; a completion written before the hard deadline is never relabeled as timed out. *Amended by T77 (parity D21):* the 5-second SIGKILL escalation after a headless stop is a referenced timer again, as in v2.9.2, so it fires also when it is the parent's last handle.

**D8. Resume.** A resume accepts a run id or a session file. Its two guards (the child ended under context pressure; a time limit that forbids resume stopped it) are checked in the resume itself, so every caller gets them. The overlay's explicit operator override applies only to the attempt that received it. A resume reserves its session in this process before any asynchronous step, so a second resume of the same session is refused even when both start together. The earlier exit record is cleared before the child starts, as in v2.9.2. The block-resume verdict stays until the new run ends; the new run's outcome then replaces or removes it. A failed start, or a parent that dies during the run, therefore leaves the verdict in force. Two Pi processes that resume one session at the same moment, with no verdict, are not covered; v2.9.2 has the same gap. (amended 2026-11-20, T74; parity D17, D07, D14; owner 2026-11-20T11:30Z) A resume by run id takes the session file from the run's record. The record refuses with its own reason only for a fact no later run changes (no session file, a verified fan-out attempt); a time-limit or context-pressure reason is left to the two guards, which read the session's current state, so an old record cannot refuse after a later successful operator resume removed the verdict.

**D9. Launch admission.** (amended 2026-11-20, T74; parity D17, D07, D14; owner 2026-11-20T11:30Z) There is no cumulative launch cap and no PI_SUBAGENT_LAUNCH_CAP. Admission limits only the concurrent spawn width of v2.9.2: a launch, a resume or a verified fan-out takes its spawn slots before any side effect and gives them back when the child never starts, so a 65th sequential launch starts. A launch that the spawn width refuses starts nothing and is an error result. Superseded text: a parent started at most 64 runs between two session starts.

**D10. Missing extensions.** Amended by parity decision D18 (owner, 2026-11-20T11:30Z, parity round 1): a launch and a resume pass the configured extension list to Pi as v2.9.2 does, with no pruning. A local path that does not exist and an npm or git package that is not installed reach Pi as configured; an uninstalled package uses Pi's temporary installation. A resume passes its saved list as saved. The exact pi-subagents package check stays: only the exact npm name, this package's root or declared entry, or an installed copy whose manifest has this package's name counts as the spawning extension, so a lookalike path or package does not suppress it. An empty explicit list still means no extensions, unlike no list.

**D11. Takeover.** After a takeover, nothing in the child requests shutdown. A provider error, a third run that ends at a tool call, or a recovery that runs out is shown in the pane, and the pane stays open until the person closes it or re-arms auto-exit. A completion call after a takeover records the result in the child session and writes no exit record (D12).

### Results

**D12. Completion call.** *Amended by T72 (parity D01 revert; owner 2026-11-20T11:30Z):* as in v2.9.2 (cf6dbf4), an auto-exit child, pane or headless, has no subagent_done, no completion nudge, no completion-call brief line and no oversize refusal; it exits after its answer and its result is untyped from its last message. A headless child with auto-exit off keeps the zero-argument subagent_done, whose result is untyped. caller_ping keeps the v2.9.2 availability and wording, without a refusal; its message is the report and it stays typed blocked from the exit record; a ping that loses the exit record to an earlier end fails and never changes the result. The launch schema, the data check and its retry are removed. The parent still reads typed calls, nudge entries and data errors of older sessions. A caller_ping is a typed result with outcome blocked: its full message is the report and only its rendered summary is cut to 1,500 characters; a blank message is refused without using up the one ping. A manual pane child (a pane child with auto-exit off, [manual] in D19) cannot end by itself, as in v2.9.2: it has no completion tool, also after a resume and without a deny-tools entry, and it ends only when a person closes the pane; its record is untyped (owner, 2026-11-20). Before T72 a completion call took outcome, summary, artifacts and data, with a refusal over the limit and an optional launch schema; the parent still reads such calls in older sessions and types their results by the old rule (a valid outcome and a non-empty summary).

The report comes from this run only: the last assistant text after its launch or resume and, with a subagent_done call, before that call. It is never fork history or an earlier run's text. In older sessions a nudge entry still marks the report boundary as before T72. *Amended by T77 (parity D12; owner 2026-11-20T11:30Z):* for an untyped result the v2.9.2 (cf6dbf4) source rules apply inside this run, up to a completion call that ended it (one selector, selectUntypedReport, for session entries and process output): the last assistant text; after a tool-use turn without text, the trailing tool result that is not subagent_done or caller_ping; with neither, a headless child's stdout after a clean exit, else the last assistant text before the boundary, else a failed child's stderr in a runtime-owned summary. A zero-argument subagent_done therefore keeps the tool output before it. A child without a transcript (T73) uses its stdout on any end. A final assistant turn without text and with a terminal stop reason is runtime text, not the report: it fails a clean exit with that reason, as in v2.9.2.

Since T72 no child gets a nudge, and a child never fails for a missing call. A child in report-only wrap-up (D7) has no completion call; its result is untyped, built from its text on the original deadline. *Amended by T77 (parity D21):* a wrap-up that ends on its own shows its report outcome, as v2.9.2 filed it completed (done after a clean exit; failed after a nonzero exit, a child error or an empty terminal stop); in each of these its record keeps the time limit with wrapUp true, it is ended by the time limit, and its rendering names the limit. It stays untyped: a completion call or ping from before the restart never decides it. Only a hard-deadline kill is timed out. After a takeover a completion call is not the end of the run: the parent still shows it running and delivers nothing. When the pane closes, the result uses the last completion call if no assistant text came after it, else it is untyped and built from the last text.

(Withdrawn by T72, D01 revert: a launch names no JSON schema, and a child's completion carries no data. A record of an older session can still hold data or a data error.)

**D13. Result record.** One result has one record: run id, name, agent, title, model ref, outcome (done, partial, blocked, failed, timed out, cancelled), typed, summary (at most 1,500 characters), report file, session file, artifacts, data, data error, end time, elapsed time, exit facts, time-limit facts, context usage, and whether the run can be resumed, with the reason when it cannot. Each run has its own folder in a results folder under the parent session's artifact folder; the extension does not delete it. A launch and a resume reserve the run id by creating that folder exclusively before the id appears in any reply, and draw a new id on a collision, so one run never replaces the files of another run. The parent process that watched the run publishes the result when it ends: first an immutable report file for this revision, then the record under a temporary name, renamed over the old record. The record is the commit point: a reader sees the old record with its old report, or the new record with its new report, and a record never names a missing or partial report. A later revision for the same run id adds a report and switches the record; only a verified fan-out retry does that (D18). A failed write keeps the summary in the result text and adds "report not saved: <error>"; a result never names a path that does not exist. *Amended by T77 (parity D12):* the watching session also keeps the full report in memory. Every delivered, waited and replayed copy stays capped (D14, D15); only an explicit lookup by run id (D16) appends "Full report (not saved to a file):" and the full report, the one copy that can exceed 1,900 characters.

When the results folder cannot be written, service degrades: the watching session keeps the record in memory, so lookup and the recent list (D16) still return it until the session closes or the process exits; the record keeps the session file when there is one; and the person sees a notice of the storage failure outside any script. Durable recovery after a storage failure is out of scope.

Results exist only for runs that end while their parent process watches them (owner, 2026-11-18); verified fan-out is the one exception (D18). A child with parent-close-policy: continue that is still running when its parent process exits gets no result; its session file and exit record stay for a resume by hand. A no-session child runs in Pi's in-memory mode (--no-session) as in v2.9.2, under both parent-close-policy values; its report comes from its process output, else from the final text (Pi print mode's stdout text) that the child writes into its exit record, through the one untyped report selector (D12); the parent neither waits for nor deletes a transcript at shutdown, but deletes the launch seed (it holds the parent conversation, which in-memory mode never reads) before shutdown returns (T73 fix round 1). Only a strict time-limit wrap-up persists it to the private temporary session file that v2.9.2 uses for that case: the restart reads the interrupted transcript from it, the watcher deletes the file after the result is published, and an orderly detach hands the deletion to the child's exit. Such a run cannot be resumed, and its record says so; no result is promised after the watcher exits (amended: owner, 2026-11-20T11:30Z, parity round 1, D13 revert).

**D14. One assembler, one rendering.** One pure module turns the facts of a finished run (how it ended, the session entries of this run, the completion call if any) into a record and a report text. Every path uses it: headless and pane children, a time-limit wrap-up or kill, a stop, a watcher error, a ping, and a verified fan-out winner. Without a completion call, the summary is the start of the report cut at a line end within the limit, marked untyped. One renderer turns a record into the parent's text: a header line (name, agent, outcome, elapsed time, typed or untyped, and "data error" when present), the summary, and a footer with the report file, the run id, the reason a run cannot be resumed, and the context usage line when the agent asks for it. Everything around the summary, warnings and the verifier footer included, is at most 400 characters, except for a long report locator as stated below. The footer names the report file by the shortest form that Pi's read tool resolves: the absolute path, the path with the home folder as ~, or the path relative to the parent's working directory. When that form still does not fit the 400 characters, the text around the summary may exceed 400 characters by the excess length of the locator only, and the summary is cut further, with a cut mark, so the footer keeps the whole locator and the whole text stays within 1,900 characters (a macOS path has at most 1,024 characters). A lookup returns the same text. The session path and the resume command line leave the text.

**D15. Delivery, at least once.** When a watched run ends, its result is written to its files (D13) and then handed over by itself: to every wait that is waiting for that run, or else as a message. Messages leave at the next turn boundary, or at once when the parent is idle, and start a turn; all results queued at one boundary leave as one subagent_result message. A wait that starts while a result is queued takes it from the queue. A result that a wait returned, or that a committed message carries, is delivered. The extension does not hand it over again by itself and does not check whether the model read it; copies come only from a lookup (D16). Duplicates are accepted; a copy over the size limit is not (owner, 2026-11-18). For example, a wait reply and a committed message can both carry one result into the next request: two copies of at most 1,900 characters each, one run. Edges:

- A wait whose reply does not reach its caller because it was aborted puts the results it took back in the queue.
- Esc while the turn settles: results committed in that aborted turn start no turn and enter the next request when the person types (owner, 2026-11-18). Runs that end later still start turns. An abort before the settle step starts parks nothing: Pi then skips the before-settle hook (extensions.md:336), and queued results leave as soon as the parent is idle. No result waits for a prompt in any other case.
- A workflow script that fails after its wait gets nothing back by itself; the parent sees the error and recovers by lookup.
- A closed or replaced session gets no more deliveries; its results stay in their files for a lookup after resume.
- A launch that waits by the existing rules (agent definition, headless or one-shot parent, a launch next to another call) takes its results through the same queue. A batch of only launches still ends the parent turn for direct calls (see D16 for codemode).

One module owns the queue. Its rules are tests at the extension boundary:

- R1. Every copy of a result that enters the parent, automatic or looked up, is the capped rendering; the report never enters by itself.
- R2. A watched run's result is in its files before it is handed over, and it is handed over unless the session closed first.
- R3. A queued result leaves at the next turn boundary, or at once when the parent is idle, and never waits for the person to type, except after Esc while the turn settles.
- R4. A wait that returns or is aborted leaves no result that it took and did not deliver.

**D16. Wait, lookup and launch replies.** subagent_wait takes run ids (default: every run of this parent that is running or queued), a mode (all or any, default all) and an optional time limit in seconds. It returns when the mode is met or the limit passes, and at once when there is nothing to wait for. The reply has the rendered results and, as structured data, the records and the pending ids. Two waits on one run both get its result. Esc stops the wait; its runs keep running and report by message. Esc during a launch or resume that waits stops the child it waits for, as in v2.9.2; the results the wait already held are handed back as for subagent_wait (amended 2026-11-20, parity D04a; owner 2026-11-20T12:00Z).

A lookup is a wait on a run id that was already delivered: it returns the same rendering at once, from the record file (owner, 2026-11-18). With the recent parameter, the wait returns at once with one line per ended run of this parent session, the last 20, newest first by the end time in the record (equal end times sort by run id), from its results folder or, after a storage failure, from the session's memory (D13): run id, name, outcome, end time, at most 1,900 characters. The window is 20 runs: an older run is found only by its run id, and the list never returns full results. A lookup changes no state and creates no obligation. A named run that is still active takes part in the wait like any other run. A run id that is neither active nor recorded gets the answer "no result record", with the session file from the launch metadata when this process knows it, and never a made-up path.

The launch and resume calls return structured data per child: run id, name, agent, model ref, session file (data only, not text), pane or headless, and state, started or ended, with the record when ended. When a later child of a batch fails to launch, the reply is an error result whose structured data holds a failure discriminator, the failed child (position, name, agent, error) and the started children's data, so a script can branch to recovery on the object alone, also when a sibling has already ended, and wait for or stop the started children. Inside codemode a launch returns at once unless it waits by the rules of D15. The mixed-batch rule and the launch-only turn end apply only to direct calls: a tool_result handler cannot set terminate, and codemode does not pass terminate on. A script gets a nested launch's structured data instead of its text, so the model may never see the launch reply; the rule against doing delegated work is therefore in the index (D19).

**D17. Stubs: deferred.** Version 1 does not remove delivered results from the parent context. Revisit when Pi offers a final read-only dispatch hook that shows what a request carries, or when measurements show that capped summaries still dominate parent input (owner, 2026-11-18).

**D18. Verified fan-out.** The feature and its protocol stay as in v2.9.2: supervisor, delivery lease, receipt written when the delivery id appears in the parent session file, authorized recipients, adoption by the origin or an authorized ancestor after the origin exits (the one exception to D13's watched-only lifetime), retry generations, candidate isolation, no resume of an attempt. Only the text changes: the winner report goes through the assembler and the renderer, with the verifier footer inside the 400-character envelope and the full report in a report file. The delivery id stays in the message details, not necessarily in the text; the capped text keeps the staged or not-applied fact, the report keeps the full provenance, and an unauthorized notice holds no winner report. A retry's newer generation replaces the run's files (D13). A winner whose receipt is never confirmed, for example one returned into a workflow script, may be adopted again; that copy is capped too, which D15 accepts. In a print-mode parent, adoption still starts no extra turn. Its slots follow D6.

### Agent context, just in time

**D19. Index.** The roster message is no longer sent. At the start of each prompt the extension writes one named system-prompt section. Pi stores it with the session, patches it only when it changed, and keeps it through compaction, resume and reload. The section is at most 4,400 characters: three fixed lines and one entry per agent, its line and its model lines.

    Helpers: launch with subagent (a children list). A result arrives as a message; subagent_wait joins now or looks up a run id. A helper sees only its task text unless marked [fork].
    Do tiny work yourself. Use each named helper once, no substitutes. Do not redo delegated work. Ask when ownership is unclear.
    More tools: subagent_wait, subagent_resume, subagent_kill, subagent_agents (search, full detail).
    - reviewer: <first 100 characters of the description>
    - design: <first 100 characters> [pane] [manual]
    +488 more: subagent_agents with a query

Pinned agents come first, by name; then the others, by name; entries are added until the limit; the last line counts the rest. A flag appears only when the agent differs from the common case: [pane], [fork], [manual] (stays open until a person closes it), [waits] (the launch call waits). Each agent line is followed by the v2.9.2 roster model lines, verbatim (cf6dbf4 src/agents/agent-list.ts renderDefaultModelLine, renderModelsLine): `  default_model: <ref>` and `  models: <default> | <allowed…>` or `  models: any model ref`, no models line when allow-model-override is false; one exception keeps D22: a model whose colon suffix is no Pi level (`prov/m:free`) with a separate thinking level shows as the ref the child runs on (`prov/m:free:high`), where v2.9.2 dropped the level; an agent line and its model lines give way as one unit, so a parent picks an allowed model and launches in one call (amended, owner 2026-11-21: the owner's 10 agents render at most 3,867 characters with them, +2,178 characters or about 545 tokens once per session in the cached prompt; the limit is that plus 533 characters of headroom, about one more agent). No rules block; the second line keeps the v2.9.2 routing rules in short form (D06, owner 2026-11-20T12:10Z). The index names only tools Pi lets the session call: without subagent_wait the first line drops its clause, and without subagent_agents a last line names the agents that have no line (descriptionless ones too), and agent lines give way to it until every name fits. A prompt start runs no multiplexer probe; [pane] and [manual] follow the detection of the latest launch, and before the first one a UI session gets them with a line that they need a multiplexer. When another extension's whole prompt replaces the sections, before or after this handler, the index goes into each request as a leading message, not stored and without changing that prompt; a child's earlier whole prompt still gets the section appended. An agent without a description gets no agent line: subagent_agents finds it, and without subagent_agents the names line names it (amended by T86; v2.9.2 left it out of the roster, and the index left it out even when it was the only agent). [fork] marks a child that starts with the parent transcript: a no-session child outside a strict wrap-up runs in Pi's in-memory mode, which ignores the seed (D13), so it gets no [fork] whatever its session-mode (amended by T86; v2.9.2 derived the session from the seed mode). A child that may launch children gets the section filtered by what it may launch; a child that may launch nothing gets no section and no launch tools, as in v2.9.2.

**D20. Agents tool.** subagent_agents covers only the agent definitions that the caller may launch. With a name it returns that agent's full definition view: description, default model ref, accepted model refs grouped by provider, kind of child, session mode, limits, and what it may launch. The default model ref is shown only when it round-trips: a call that names it, through the launch resolver, the grant check and Pi's own model resolution and level clamp, runs on the same model at the same level as a launch without a model (D22). Otherwise the line says what a launch without a model does: Pi refuses it (a bare default that several providers carry and no accepted list), or it runs on a model and level that no call can name (for example a qualified non-reasoning default whose grant keeps the inherited level), so the caller leaves the model out. When the default's grant cannot resolve, every launch fails and the accepted list shows its refs as configured, not usable. Launch behaviour and grants do not change (T86 fix round 1). The session mode is the session the child gets: "fresh chat in memory" for an in-memory no-session child (amended by T86). With a query it returns the best matches (default 5), one line each. With no argument it returns the count and one line on how to search; it does not list pinned names. A malformed agent file is named here with its parse error when its name is one that the caller may launch. The overlay keeps its full operator view.

**D21. Tool declarations.** The launch tool accepts both v2.9.2 forms: one child as top-level fields, or a children list up to the spawn width, each with agent, name, title, task, and optional model and thinking (T72 removed schema); an empty list falls back to the top-level fields. Only a children list sent as a JSON string is parsed; any other JSON-looking argument string (wait ids, legacy completion data or artifacts) keeps its string type (amended 2026-11-20, parity D05; owner 2026-11-20T12:00Z). Each rule is stated once: the rule about leaving the model unset sits in the model parameter only. The launch tool is declared in every session that may launch; the registration rules of v2.9.2 stay (no agent definitions, deny-tools, a spawn depth of zero). The wait, resume, stop and agents tools are registered as deferred when the session has codemode or tool search active, so their declarations cost nothing until asked for; in a host with neither they are declared directly (deferral kept as a context exception, parity D07). The choice is made at session start, after Pi has bound the runtime, because the active tool list cannot be read while the extension loads. A deferred tool stays callable from codemode when it is not active, so each tool also checks at call time that the caller may use it. (amended 2026-11-20, T74; parity D17, D07, D14; owner 2026-11-20T11:30Z) Stop and resume have their own grants, as in v2.9.2: a session that may not launch can still stop and resume its children, and only an explicit deny-tools entry for the stop or resume tool removes it. Wait and agents still require a callable launch tool. Tool descriptions are one sentence. There is no separate prompt snippet per tool.

**D22. Model resolution.** With no model in the call, the child runs on the agent's default. With a model in the call, exact model ids, the bare-id provider tie-break and level precedence behave as in v2.9.2 (cf6dbf4; parity D08, owner 2026-11-20T12:10Z): an exact `provider/id` names that model; an id without a provider that one provider carries takes that provider, and one that several carry takes the parent's provider on launch and the previous run's provider on resume, else it is refused as ambiguous. The level is the call's `:level` suffix, else the thinking parameter, else the agent's level (on resume: the previous run's level), else the parent's; an accepted list checks that level and never picks one. A literal id whose colon suffix is not a Pi level stays whole. Only when no exact id matches does the call model count as a fragment: the provider part must be equal and the model part may be a fragment, and exactly one accepted model must match. A fragment that matches two models of one provider is refused. A fragment named without a provider that matches under several providers takes the provider of the agent's default model, and is refused when that provider is not among the matches. An agent without an accepted list takes any exact ref that Pi knows, and a fragment is matched against Pi's model list by the same rules. An agent with no accepted list and no default model runs on the parent's model, as today. The agent's default model counts as accepted even when its accepted list does not name it, as today. With no model in the call, that grant resolves as in v2.9.2: a bare default that several providers carry takes the parent's provider, the same ref the child runs on (parity M34, owner 2026-11-20). Every refusal while matching a fragment names at most 8 matching candidates, grouped by provider, and points to subagent_agents with the agent name; a resolved model that the accepted list refuses at its level gets the v2.9.2 refusal that lists the allowed models. An agent definition whose override switch is off ignores a model in the call and says so in the launch reply. A resume with a model applies the same rules. The record keeps the display ref (the registry ref a bare default runs on, D23) apart from the invocation ref (what Pi got as `--model`); resume and timeout wrap-up replay the invocation ref. A record written before the invocation ref replays its model and level as the launch passed them (bare when the call was bare), and a record with only the display ref replays that. On launch the default grant resolves like the child's default (v2.9.2); on resume it is the definition as written, else the inherited parent ref. There is no alias table and no rewrite hook.

**D23. Facts at the point of use.** The launch reply has one line per child: agent, name, run id, the model ref that runs, pane or headless. It has one line for the batch that says how results return. Warnings follow. An unknown agent name is refused with the v2.9.2 error: the requested name and the search locations, no substitute names (D06). A launch that fails partway names the children that started (D16).

**D24. One bad file.** A malformed agent file is skipped. The other agents load. A launch of the bad agent is refused with its parse error. A malformed project file whose name matches a valid global agent is refused the same way; the global agent is not launched in its place. The person sees one notice per session that names the file. A malformed file that a valid definition of the same name shadows is listed apart, and the notice does not call that agent refused (parity D19).

### Children

**D33. Child prompt parity.** A child keeps the whole-prompt returns of v2.9.2 (the time-limit and wrap-up text, the composition of skills and appended system text) until one slice moves them to named sections and appended text and proves the same behavior: skill visibility for =auto and =manual skills, an appended system text that the child inherits, the time-limit and wrap-up text, the fork boundary, and a child whose only tool host is codemode. That slice is not on the path to either goal.

### Workflow scripts

**D25. Recipe, not a runner.** The README gets one recipe: a workflow script launches a batch, waits with a time limit, checks outcome, typed and data error, and returns a digest of at most about 1,500 tokens with report file paths and run ids. On a time limit it returns the pending ids and says that their work must not be redone. After a failure the parent recovers with subagent_wait, by run id or with the recent list, and does not launch the batch again blindly. The recipe states the limits: at most two codemode workers per Pi process by default (PI_CODEMODE_MAX_WORKERS), and a waiting script holds one; a third script waits up to 60 seconds, or its own shorter deadline, then fails without running; a cancelled worker keeps its slot until it exits; a waiting script must not depend on another script; a script cannot be resumed from the middle; a steer is not an interrupt; time and random values come from outside the script if a rerun should repeat. A second recipe shows a child that may launch children as the coordinator of a batch. The extension ships no agent definitions.

### Backends

**D26. Backend interface.** One interface replaces the per-backend branches. A backend can: say whether it is available; open a surface with a placement request; start a command in a surface, or start a program directly as the surface's own process; read the last lines of a surface; close a surface. Renaming the caller's tab and its workspace are optional abilities; with neither (Rex), set_tab_title reports the multiplexer unavailable with the v2.9.2 setup hint and sets no title (parity D10). Two further optional abilities: report that the surface's process exited with its code, signal and reason; and accept a status record. Shared code asks for an ability and never tests the backend's name. cmux, tmux, zellij, wezterm and old herdr move behind the interface with no change in behavior, pinned by their existing fake-binary tests; D34 then changes old herdr's identity names only. One contract suite runs against every backend.

**D34. Environment boundary.** On every backend the child launcher builds the child's environment, as in v2.9.2: the parent's environment minus the names that deny-env and PI_SUBAGENT_ENV_DENY match, then the identity names of the child's own surface, then the controlled overrides. Values from the env frontmatter are overrides and are not filtered, as the README documents. Which surface names the identity step copies depends on the backend (owner, 2026-11-18):

- herdr-core, Rex and old herdr copy only documented identity names, as exact names with no pattern. herdr-core: HC_TERMINAL_ID, HC_TERMINAL_SOCKET and HC_SCOPE. Rex: REX_SESSION and REX_BLOCK. Old herdr: HERDR_ENV and HERDR_PANE_ID, required, and HERDR_TAB_ID, HERDR_WORKSPACE_ID, HERDR_BIN_PATH, HERDR_SOCKET_PATH and HERDR_CONFIG_PATH when present (read in src/mux/herdr-work.ts, src/mux/herdr-surfaces.ts, src/mux/herdr.ts and test/mux/herdr-work.test.ts; a live check on old herdr confirms the list before the change lands). TERM and COLORTERM stay as on every backend. The launcher first removes these names from the parent's environment and refuses to start Pi when a required name is missing from the child's surface, so a child never carries the parent's identity. An env override of a non-identity name still works; an override that names a required identity name is refused before Pi starts. On these three backends a name that only the multiplexer daemon has never reaches the child.
- tmux, cmux, WezTerm and Zellij keep the v2.9.2 patterns TMUX*, CMUX*, WEZTERM* and ZELLIJ* in version 1. Known limit: a name with such a prefix that the pane carries, for example a denied TMUX_PROBE_PRIVATE that only the daemon has, still reaches the child on these four backends, so deny-env does not hold for it. Revisit a backend when a live check on it confirms its exact identity names. A backend claims parity only after a presence check with synthetic marker names on launch, resume and time-limit restart; the check prints only whether each marker is present, never an environment.

**D27. herdr-core backend.** It is selected when the parent runs in an herdr-core terminal and the Herdr app answers. A pane child is started through herdr-core's API with the parent's terminal as caller, notes off (herdr-core types a note into a parent that reports OSC 7501, as Pi does), and a label with a key unique to the launch. The terminal's program is the child launcher with its capsule, which starts Pi with the environment of D34; the extension passes no environment map, because herdr-core adds its daemon environment to any map (owner, 2026-11-18). There is no shell, no pasted command and no ready delay; the launcher passes Pi's exit code and signal on. The child takes its surface name from its own HC_TERMINAL_ID. The backend subscribes to events by the launch label before the start and takes the exit from the finished event; after a dropped stream it subscribes again first and then reads the terminal state once, so an exit between the two is not lost, and it never removes a terminal before it has read the exit facts. When a start request gets no answer, the backend looks the label up for a bounded time and uses the terminal only when it finds exactly one; otherwise the launch fails and names the label. It never sends a second start request. Closing is kill, then remove.

Placement, checked live on herdr-app 0.1.16: the split command splits the focused pane and moves focus, so the backend saves the app's focus, focuses the parent's pane, asks for the split, and restores the saved focus; the parent pane may show focus for under a second. These steps are one transaction: the extension runs at most one at a time per Herdr app, and restores the saved focus also when a step fails. When the split fails, the child gets a tab in the parent's space through a label, which moves no focus. A child outlives the parent only with parent-close-policy: continue; otherwise the extension stops it when the parent session closes, because herdr-core ties children to the shell, not to Pi. When Pi dies without an orderly shutdown, its children run until the parent terminal's program ends. Detection, placement planning, focus restore and test fakes come from upstream PR #33, credited in the commit. Headless children stay plain processes.

**D28. Rex backend.** It is selected when REX_SESSION and REX_BLOCK are set and the rex binary is found, on PATH or else in REX_BIN_DIR (inside a Rex block rex is not on PATH). At first use it reads the API revision from rex whoami and accepts revision 16, on which the live checks ran, and later revisions that the Rex ticket confirms; other revisions make the backend unavailable with a hint. A pane child opens in the parent's Rex session, which the backend names on every create (-s with the parent's REX_SESSION). PI_SUBAGENT_REX_PLACEMENT chooses the placement (amended 2026-11-20, T71): window, the default, opens every child in a new window of that session (rex window new -s <session> <label> --focus=false); split opens it as a split to the right of the parent block (rex split -b with the parent's REX_BLOCK), at most 2 per window, then in a new window of the same session (rex window new); each create has --focus=false. An unknown value fails as an unknown PI_SUBAGENT_HERDR_PLACEMENT value does. An agent's env frontmatter can set the variable for its own launches; on resume the Herdr precedence applies (persisted per-agent env, then the current parent default, then the persisted policy). A child in a separate Rex session is not visible in the app, and switching the app to another session needs the app's Remote Control setting (owner's observation; Rex docs). The launch command is sent as one line of text, then Enter as a key; multi-line input is not used; it runs the child launcher, which builds the environment from its capsule (D34), because the caller's environment does not reach a Rex block. The child gets a label with a key unique to the launch: on a split the label belongs to the block; on a new window it belongs to the window, whose first block is labeled shell. After a create that fails with a request timeout, the backend looks the label up in the parent's session first, because such a create can leave a live block: for a split, the block with that label; for a new window, the window with that label and its one block. It uses the result only when exactly one matches; on zero or several matches it sends nothing, closes nothing and creates nothing, and the launch fails and names the label. A connect timeout creates nothing. It never sends a second create. The capture is cut to the last lines with at most 256 KB buffered, because rex capture has no line limit. The backend never sends to or closes the parent's own block, or a parent block that no longer exists. Remote Rex servers and minimized layers are out of scope.

**D29. Detection order.** PI_SUBAGENT_MUX forces a backend, also when markers of several backends are present. Otherwise the order is herdr-core, Rex, old herdr, cmux, tmux, zellij, wezterm. Old herdr is detected only with its own pane variable, so the herdr variables that linger in a shell do not match.

**D30. Work status.** On herdr-core and Rex the parent publishes one OSC 7501 side record with the count of outstanding children. A run counts from its launch until its result is delivered (D15) or a stop or session close releases it; a message with several results releases each. The record is cleared at zero, and the extension clears only its own record, never Pi's status. One writer serves both backends; old herdr keeps its present reporter and the v2.9.2 (cf6dbf4) release rule: a delivered result counts until the parent has read it and settled idle (parity D11). Live checks showed that herdr-core stores the record and that Rex reads back a default record with an empty id; that a named side record coexists with Pi's own record and is cleared alone is not checked live yet (T50); whether either app draws it is unknown.

### Rollout

**D31. One switch.** The owner's Pi keeps loading the upstream package until every ticket has landed on the branch and both goals pass. Then the package entry and the agent definitions that name the upstream package switch to the local fork in one step. Before the switch, one command copies the package configuration, every agent definition that the switch changes, and both stand-in extension files into one snapshot folder; one restore command puts all of them back. A dry run goes forward and back once, with a child session saved before the switch, before anything is deleted. The owner approves the switch and, later, the removal of the stand-in files.

**D32. Upstream v3.** When v3 appears, the owner decides between a rebase and a port. D4 keeps both cheap. This spec plans neither.

## Testing Decisions

A good test calls the extension the way Pi does, or calls one pure module with plain data, and checks what a parent, a child or a person can observe: tool replies, messages, files, calls to a fake multiplexer binary. It does not reach into a watcher's private state.

Seams, highest first:

1. **Extension boundary.** The existing pattern: a mock Pi that records tool registrations and fires events, fake multiplexer binaries on PATH, fake child processes. All tool, index, launch, stop, resume and delivery behavior is tested here, including the delivery cases of D15: a boundary append, Esc while the turn settles, an aborted wait, two waits on one run, mode any and all with simultaneous ends, a partial time limit, a session replacement, a failed script with recovery by lookup, and the recent list. Tests assert a next model request or a wait or lookup reply that holds the result, and that every copy is within the cap. Prior art: the launch result, wait, result router, spawn width and interactive delivery failure suites.
2. **Result assembler** (new pure module, D14): every outcome, the typed and untyped paths, the report source rules of D12, the limits and the rendering length.
3. **Backend contract suite** (D26): one set of tests that each backend passes with its fake binary. Prior art: the herdr, cmux, zellij and poll suites.

The ticket draft maps each of the 13 replays and the three roster defects that were only read to one acceptance check. A scratch test that asserts the buggy value is turned around, so the regression test is red on cf6dbf4 and green after the fix. The two delivery defects get these outcomes under D15. A result that arrived twice in full (replay 1): the waiting launch's tool result holds it, the full report never enters the parent, and any other copy is within the cap. A result that nobody delivered (replay 2): it goes out as a message. The target charts of the run, the auto-exit child and the index specify D5 to D7, D11 and D19; their rule names and R1 to R4 are test names.

Live validation follows AGENTS.md: temporary agent definitions and session folder, parent and child sessions inspected, outcomes classed as duplicate, auxiliary or clean yield, interactive parents prompted after startup. The live matrices cover detached, blocking, Esc, mixed, codemode-only and one-shot parents, a failed script with recovery by lookup, resume, time limits, takeover, fork, frontmatter and environment-variable branches in both states, and the lifecycle of every installed backend, herdr-core and Rex included, with presence-only checks of deny-env and the child's identity on launch, resume and time-limit restart; a backend that is not installed or not reachable without restarting the owner's server is reported as not run, and no parity is claimed for it. A skipped live check is not a pass. Live runs use two models of one family, and the behavior checks run once more on a model of another family; the owner names the refs for each run, and they go neither into the repository nor into the tickets.

While a slice is built, only the affected tests run. The full suite and the structure gates of AGENTS.md run once per landed batch and once on the candidate commit (owner accepted the cut, 2026-11-18).

## Out of Scope

- A workflow runner, sandbox, journal or resume of scripts inside the extension; token, cost or turn budgets across children.
- Enforcement of a single writer; the rule stays one line of the index.
- Proof that the model received a result (receipt records, a received state, request inspection), and handing results back after a failed script (owner, 2026-11-18).
- Removing delivered results from the parent context (D17, deferred).
- Changes to the verified fan-out protocol beyond its text (D18). A known v2.9.2 race stays: a late receipt for an old generation can make adoption skip a newer generation in the same session.
- A resume reservation across Pi processes (D8).
- Results of runs that end after their parent process exited (D13), and any daemon that would write them.
- Durable recovery of a result after a storage failure (D13).
- Exact identity names for tmux, cmux, WezTerm and Zellij (D34 known limit).
- A way to end the parent turn after a script that only launches; Pi has no mechanism (D16).
